# System Architecture & Core Concepts

## 1. What is Attendly?

**Attendly** is a local-first, privacy-focused web application tailored for students of SVKM / NMIMS (Mukesh Patel School of Technology Management & Engineering). Its primary purpose is to transform confusing, dense attendance records generated by the university's SAP portal into an intuitive, actionable, and visual attendance dashboard.

Students can see:
1. **Accurate Attendance Statistics**: Real percentages calculated accurately, handling university quirks like "Not Updated" (NU) classes.
2. **Bunk Buffer & Recovery Calculations**: How many upcoming lectures a student can safely miss, or how many consecutive lectures they must attend to meet the mandatory 80% threshold without floating-point math errors.
3. **Curriculum & Lecture Projections**: Projections based on the NMIMS 15-week fixed semester schedule and credit-hour curriculum rules (e.g., distinguishing theory classes from 2-hour labs).
4. **Interactive NU Simulation**: What happens to overall and course attendance if unmarked (NU) classes turn out to be Present or Absent.
5. **Direct SAP Portal Automation**: An automated Playwright bot that logs into the university SAP portal in a live Pixel 7 mobile viewport and downloads the official attendance PDF directly without requiring manual downloading.

## 3. End-to-End Data Flow

### Path A: Manual PDF Upload
1. The student downloads their attendance PDF from the SAP portal.
2. The student drags and drops the PDF into the `UploadZone` component on the frontend (`http://localhost:5173`).
3. The frontend sends the PDF binary via `POST /api/attendance/upload`.
4. FastAPI validates the file extension and size (max 10MB).
5. `parser.py` parses the PDF using PyMuPDF:
   - Validates that the file has an authentic `%PDF` header.
   - Extracts student metadata from Page 1 (Name, Roll No, SAP Student ID, Academic Year, Semester).
   - Scans line-by-line to parse attendance rows: `[Sr No, Course Name, Date, Start Time, End Time, Status]`.
6. For each row, `normalizer.py` cleans the course name by removing section numbers (`T1`, `P1`, `U1`), lab markers, and batch codes (`MBA Tech CE E`).
7. `calculator.py` aggregates the records:
   - Grouping by clean course name.
   - Summing `Present (P)`, `Absent (A)`, and `Not Updated (NU)`.
   - Computing percentage as `(Present / (Present + Absent)) * 100`.
8. `database.py` stores the records in `attendly.db` (marking any older dataset as non-current).
9. The backend returns the complete dataset as JSON to the frontend.
10. The frontend navigates to `/dashboard` and renders the metrics.

### Path B: Automated Portal Fetch (Live Playwright Bot)
1. The student enters their SAP Student ID and Portal Password into `UploadZone` or the `SyncModal`.
2. The frontend triggers `POST /api/attendance/fetch`.
3. `scraper.py` executes in a dedicated Windows Proactor background thread:
   - Launches Chromium in a Pixel 7 mobile viewport (`412x915`).
   - Emulates mobile browser headers (bypassing desktop portal CAPTCHA checks).
   - Navigates to `https://sdc-sppap1.svkm.ac.in:50001/irj/portal`.
   - Fills Student ID and Password, and clicks Logon.
   - Finds and clicks **"Attendance Display for Students"**.
   - Switches to the SAP WebDynpro iframe (`isolatedWorkArea`).
   - Automatically selects the latest **Academic Year**, latest **Semester**, and **"Detail Report"**.
   - Triggers the SAP report generator button (`#WD51`).
   - Intercepts the generated PDF bytes from the embedded `<object class="lsPdfObject">`.
4. The downloaded bytes are passed directly into `parser.py`.
5. The dataset is parsed, saved into SQLite, and returned to the frontend.

## 4. Key Mathematical Formulas & Rules

### Rule 1: The "Not Updated" (NU) Rule
In the NMIMS SAP system, when a teacher has conducted a class but hasn't finalized the attendance register yet, the status is marked as **NU** (Not Updated).
- **Official Policy**: NU classes are **excluded** from the calculation denominator.
  $$\text{Counted} = \text{Present} + \text{Absent}$$
  $$\text{Percentage} = \frac{\text{Present}}{\text{Counted}} \times 100$$
- If counted is 0, percentage is `null` (displayed as `--`).

### Rule 2: Overall Attendance Calculation
Overall university attendance is **NOT** the arithmetic mean of subject percentages. Doing so would overweight courses with fewer total lectures.
- Attendly computes overall attendance across the pool of all counted sessions:
  $$\text{Overall Percentage} = \frac{\sum \text{Present}}{\sum (\text{Present} + \text{Absent})} \times 100$$

### Rule 3: Bunk Buffer & Attendance Recovery (Integer Math)
Let $P$ be Present lectures, $T$ be Counted lectures ($P + A$), and $R$ be Target Percentage ($80\%$).

1. **When Currently Above Target ($P / T \ge R / 100$):**
   How many upcoming classes can the student miss ($x$) and remain at or above $R\%$?
   $$\frac{P}{T + x} \ge \frac{R}{100} \implies x \le \frac{100 \times P - R \times T}{R}$$
   Attendly calculates:
   $$\text{maxBunks} = \left\lfloor \frac{100 \times P - R \times T}{R} \right\rfloor$$

2. **When Currently Below Target ($P / T < R / 100$):**
   How many consecutive classes must the student attend ($x$) to reach $R\%$?
   $$\frac{P + x}{T + x} \ge \frac{R}{100} \implies x \ge \frac{R \times T - 100 \times P}{100 - R}$$
   Attendly calculates:
   $$\text{needed} = \left\lceil \frac{R \times T - 100 \times P}{100 - R} \right\rceil$$

> **Precision Guarantee**: Attendly executes this using pure integer operations `(target * total - 100 * present) / (100 - target)` rather than `(0.80 * total - present) / 0.20`. This prevents IEEE-754 floating point drift (e.g. `6.000000000000015` turning into `7` via `Math.ceil`).

3. **Comparison with Semester Remaining Lectures:**
   - If $\text{needed} > \text{remainingLectures}$:
     *"Cannot reach 80%! Do not miss any more"*
   - If $\text{needed} \ge \text{remainingLectures}$:
     *"Cannot miss any more lectures!"* (e.g., student must attend all remaining 6 out of 6 to hit exactly 80%).
   - If $\text{needed} < \text{remainingLectures}$:
     *"Need to attend next $x$ lectures"*.

## 5. NMIMS Curriculum Model (15 Weeks Fixed)

NMIMS engineering semesters run on a **15-week fixed calendar**:
$$\text{Planned Lectures} = \text{Credits} \times 15$$

### Course Structure Configurations
1. **Pure Theory Courses (e.g., 3 credits)**:
   - Weekly: 3 Theory sessions.
   - Total planned: $3 \times 15 = 45$ lectures.
2. **Theory + Tutorial Courses (e.g., Discrete Mathematics, 3 credits)**:
   - Weekly: 2 Theory sessions + 1 Tutorial session.
   - Total planned: 45 sessions ($30 \text{ theory} + 15 \text{ tutorials}$).
3. **Theory + Lab Integrated Courses (e.g., Python, Signals & Systems, 3 credits)**:
   - Weekly: 2 Theory sessions + 1 Lab session.
   - Lab Rule: 1 Lab session is 2 consecutive hours on the same date, logged in SAP as 2 individual records.
   - Attendly allows toggling **"Count 2 Hours as 1 Session"**:
     - Completed Labs = Count of unique lab dates.
     - Planned Labs = $1 \times 15 = 15$ sessions.
4. **Pure Lab Courses (e.g., Data Structures Lab, 1 credit)**:
   - Weekly: 0 Theory + 1 Lab session (2 hours).
   - Planned: 15 sessions (30 raw SAP hours).

## 6. Database Schema (attendly.db)

Attendly uses SQLite with Write-Ahead Logging (WAL) enabled:

```sql
CREATE TABLE datasets (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    student_name TEXT NOT NULL,
    student_number TEXT,
    roll_number TEXT,
    academic_year TEXT,
    semester TEXT,
    program TEXT,
    report_start_date TEXT,
    report_end_date TEXT,
    institution TEXT,
    source_filename TEXT,
    imported_at TEXT NOT NULL,
    is_current INTEGER DEFAULT 1
);

CREATE TABLE attendance_records (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    dataset_id INTEGER NOT NULL,
    serial_number INTEGER NOT NULL,
    course_raw TEXT NOT NULL,
    course_normalized TEXT NOT NULL,
    date TEXT NOT NULL,          -- Format: YYYY-MM-DD
    start_time TEXT NOT NULL,    -- Format: HH:MM:SS (24-hour)
    end_time TEXT NOT NULL,      -- Format: HH:MM:SS (24-hour)
    status TEXT NOT NULL,        -- 'P', 'A', 'NU', 'E', 'L'
    FOREIGN KEY (dataset_id) REFERENCES datasets(id) ON DELETE CASCADE
);

CREATE INDEX idx_records_dataset ON attendance_records(dataset_id);
CREATE INDEX idx_records_course  ON attendance_records(course_normalized);
CREATE INDEX idx_records_date    ON attendance_records(date);
```

When a new report is uploaded or fetched, `is_current` is reset to `0` for old datasets, and the new dataset is inserted with `is_current = 1`. If deleted, foreign key cascade deletes all records.
